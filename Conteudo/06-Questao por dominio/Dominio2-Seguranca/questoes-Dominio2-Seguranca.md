## Q1

[ENUNCIADO]
Uma empresa está implementando um aplicativo em instâncias do Amazon EC2. O aplicativo precisa processar a entrada transações. Quando o aplicativo detecta uma transação inválida, o aplicativo deve enviar um chat mensagem para a equipe de suporte da empresa. Para enviar a mensagem, o aplicativo precisa recuperar o token de acesso para autenticar usando a API de chat. Um desenvolvedor precisa implementar uma solução para armazenar o token de acesso. O token de acesso deve ser criptografado em repouso e em trânsito. O token de acesso também deve estar acessível em outras contas da AWS. Qual solução atenderá a esses requisitos com MENOS sobrecarga de gerenciamento?

[A] Use um parâmetro AWS Systems Manager Parameter Store SecureString que usa um AWS Key Management Serviço (AWS KMS) Chave gerenciada pela AWS para armazenar o token de acesso. Adicione uma política baseada em recursos ao parâmetro para permitir acesso de outras contas. Atualize a função IAM das instâncias EC2 com permissões para acesse o armazenamento de parâmetros. Recupere o token do Parameter Store com o sinalizador de descriptografia ativado. Use o token de acesso descriptografado para enviar a mensagem ao chat.
[B] Criptografar o token de acesso usando uma chave gerenciada pelo cliente do AWS Key Management Service (AWS KMS). Armazene o token de acesso em uma tabela do Amazon DynamoDB. Atualize a função IAM das instâncias EC2 com permissões para acessar DynamoDB e AWS KMS. Recupere o token do DynamoDDecrypt o token usando AWS KMS nas instâncias EC2. Use o token de acesso descriptografado para enviar a mensagem ao chat.
[C] Use o AWS Secrets Manager com uma chave gerenciada pelo cliente do AWS Key Management Service (AWS KMS) para armazenar o token de acesso. Adicione uma política baseada em recursos ao segredo para permitir o acesso de outras contas. Atualizar a função IAM das instâncias EC2 com permissões para acessar o Secrets Manager. Recuperar o token de Gerenciador de segredos. Use o token de acesso descriptografado para enviar a mensagem ao chat.
[D] Criptografar o token de acesso usando uma chave gerenciada pela AWS do AWS Key Management Service (AWS KMS). Loja o token de acesso em um bucket do Amazon S3. Adicione uma política de bucket ao bucket S3 para permitir acesso de outros contas. Atualize a função IAM das instâncias do EC2 com permissões para acessar o Amazon S3 e o AWS KMS. Recupere o token do bucket S3. Descriptografe o token usando o AWS KMS nas instâncias do EC2. Use o token de acesso descriptografado para enviar a massagem para o chat.

[RESPOSTA] C

[EXPLICACAO]
A melhor solução é C. Use o AWS Secrets Manager com um AWS Key Management Service (AWS KMS) chave gerenciada pelo cliente para armazenar o token de acesso. Aqui está um resumo de por que esta é a opção mais adequada e por que as outras são menos ideais: Benefícios do AWS Secrets Manager: O Secrets Manager foi projetado especificamente para armazenar, alternar e gerenciar segredos como tokens de acesso. Ele fornece criptografia integrada em repouso usando KMS e gerencia automaticamente recuperação e descriptografia. Isto reduz a sobrecarga de gerenciamento do desenvolvedor em comparação com outras opções. Chave KMS gerenciada pelo cliente: O uso de uma chave KMS gerenciada pelo cliente dá à empresa mais controle sobre o ciclo de vida da chave de criptografia, incluindo políticas de rotação e acesso. Geralmente, isso é preferido para dados confidenciais. Política baseada em recursos para acesso entre contas: o Secrets Manager permite anexar uma política baseada em recursos política para um segredo, concedendo acesso a outras contas da AWS. Isso atende ao requisito de acessibilidade de outras contas. Função IAM para instâncias EC2: concedendo às instâncias EC2 uma função IAM com permissões para acessar segredos O Manager permite que eles recuperem os segredos com segurança. Menor sobrecarga de gerenciamento: o Secrets Manager cuida da criptografia, descriptografia e rotação do secreto, minimizando a quantidade de código e infraestrutura que o desenvolvedor precisa gerenciar. Por que outras opções não são ideais: A (Parameter Store): embora o Parameter Store SecureString possa armazenar dados criptografados, o Secrets Manager é mais adequado para gerenciamento de segredos, pois oferece recursos como rotação automática. O Parameter Store também possui limites de tamanho e rendimento que o Secrets Manager não oferece. B (DynamoDB): Armazenar o token criptografado no DynamoDB requer criptografia/descriptografia manual e manuseio da chave KMS, aumentando a sobrecarga de gerenciamento. O DynamoDB também não foi projetado especificamente para gerenciamento de segredos. D (S3): Armazenar o token criptografado no S3 requer criptografia/descriptografia manual e manuseio do KMS chave. S3 é armazenamento de objetos em vez de gerenciamento de segredos, aumentando a sobrecarga e a complexidade. Em resumo, Secrets Manager é o serviço especializado para armazenamento e gerenciamento de informações confidenciais. Isso fornece criptografia integrada, controle de acesso e outros recursos que simplificam o processo de armazenamento e recuperando tokens de acesso de forma segura e eficiente. Links de apoio: Gerenciador de segredos da AWS: https://aws.amazon.com/secrets-manager/ Serviço de gerenciamento de chaves da AWS (KMS): https://aws.amazon.com/kms/ Políticas baseadas em recursos: https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_identity-vs- recurso.html

## Q3

[ENUNCIADO]
Um aplicativo está usando grupos de usuários e grupos de identidades do Amazon Cognito para acesso seguro. Um desenvolvedor deseja integre os recursos de upload e download de arquivos específicos do usuário no aplicativo com o Amazon S3. O desenvolvedor deve garantir que os arquivos sejam salvos e recuperados de maneira segura e que os usuários possam acessar apenas seus próprios arquivos. Os tamanhos dos arquivos variam de 3 KB a 300 MB. Qual opção atenderá a esses requisitos com o MAIS ALTO nível de segurança?

[A] Use notificações de eventos do S3 para validar as solicitações de upload e download de arquivos e atualizar a interface do usuário (IU).
[B] Salve os detalhes dos arquivos carregados em uma tabela separada do Amazon DynamoDB. Filtre a lista de arquivos do usuário interface (UI) comparando o ID do usuário atual com o ID do usuário associado ao arquivo na tabela.
[C] Use o Amazon API Gateway e uma função AWS Lambda para fazer upload e download de arquivos. Valide cada solicitação na função Lambda antes de executar a operação solicitada.
[D] Use uma política do IAM no prefixo de identidade do Amazon Cognito para restringir os usuários a usarem suas próprias pastas em Amazon S3.

[RESPOSTA] D

[EXPLICACAO]
Aqui está uma justificativa detalhada de por que a opção D é a solução mais segura e apropriada, juntamente com explicações e links de apoio: Opção D, "Usar uma política do IAM no prefixo de identidade do Amazon Cognito para restringir os usuários a usarem seus próprios pastas no Amazon S3", é a melhor abordagem porque aproveita diretamente o IAM para impor controle de acesso baseado no nível do bucket S3. Os pools de identidades do Cognito (identidades federadas) permitem que você conceda credenciais temporárias da AWS para usuários, sejam eles autenticados por meio de grupos de usuários Cognito ou outra identidade fornecedores. Ao prefixar as chaves de objeto do S3 com o ID de identidade Cognito de um usuário, você cria uma separação lógica de dados dentro do bucket. A política do IAM associada à função de identidade do Cognito pode então ser configurada para permitir que os usuários acessem apenas objetos dentro de seu prefixo específico (pasta). Esta abordagem implementa o princípio do menor privilégio, garantindo que os usuários só podem interagir com seus próprios dados e não com os dados de outros usuários. Isto reduz muito o risco de acesso não autorizado. Por exemplo, a política do IAM concederia permissões como s3:GetObject e s3:PutObject apenas para caminhos como arn:aws:s3:::nome-do-seu-bucket/$ cognito-identity.amazonaws.com:sub /*, onde $ cognito- Identity.amazonaws.com:sub resolve o ID de identidade Cognito exclusivo do usuário. Isso permite que os usuários carreguem, baixe e gerencie arquivos dentro de sua pasta designada, garantindo isolamento e segurança. A vantagem desta solução é que o controle de acesso é aplicado diretamente no nível da infraestrutura AWS (IAM e S3). Não há necessidade de confiar em verificações no nível do aplicativo (como opções A, B e C) que podem ser potencialmente ignorados ou têm vulnerabilidades. É também o mais escalável e de melhor desempenho, já que o S3 lida nativamente com o acesso controle. A opção A introduz complexidade com notificações de eventos S3, que são mais adequadas para acionar fluxos de trabalho após uploads ou downloads, não para controle de acesso primário. A opção B requer a manutenção de uma tabela DynamoDB, o que adiciona sobrecarga e introduz possíveis problemas de sincronização. Ele também depende da lógica do aplicativo para filtragem, que é menos segura que o IAM. A opção C, usando API Gateway e Lambda, introduz complexidade e latência para uploads e downloads simples de arquivos. Ele também adiciona outra camada onde a segurança podem ocorrer vulnerabilidades, necessitando de validação cuidadosa na função Lambda. Políticas IAM diretamente integradas com S3 são muito mais eficientes e seguros. Portanto, aproveitar políticas IAM com prefixos de identidade Cognito oferece o mais alto nível de segurança e é o solução mais simples, escalável e econômica. Ele se integra diretamente à identidade da AWS e sistema de gerenciamento de acesso, reduzindo a superfície de ataque e simplificando o controle de acesso. Links de apoio: Grupos de identidades do Amazon Cognito: https://docs.aws.amazon.com/cognito/latest/developerguide/cognito- identidade.html Políticas IAM para Amazon S3: https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-access- controle.html Variáveis de política IAM: https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_variables.html

## Q9

[ENUNCIADO]
Uma empresa deseja compartilhar informações com terceiros. O terceiro tem um endpoint de API HTTP que o empresa pode usar para compartilhar as informações. A empresa possui a chave de API necessária para acessar a API HTTP. A empresa precisa de uma maneira de gerenciar a chave de API usando código. A integração da chave API com o aplicativo o código não pode afetar o desempenho do aplicativo. Qual solução atenderá a esses requisitos com MAIS segurança?

[A] Armazene as credenciais da API no AWS Secrets Manager. Recupere as credenciais da API em tempo de execução usando o AWS SDK. Use as credenciais para fazer a chamada da API.
[B] Armazene as credenciais da API em uma variável de código local. Envie o código para um repositório Git seguro. Use o código local variável em tempo de execução para fazer a chamada da API.
[C] Armazenar as credenciais da API como um objeto em um bucket privado do Amazon S3. Restrinja o acesso ao objeto S3 por usando políticas do IAM. Recupere as credenciais da API em tempo de execução usando o AWS SDK. Use as credenciais para fazer a chamada da API.
[D] Armazene as credenciais da API em uma tabela do Amazon DynamoDB. Restrinja o acesso à tabela usando recursos políticas baseadas. Recupere as credenciais da API em tempo de execução usando o AWS SDK. Use as credenciais para fazer o Chamada de API.

[RESPOSTA] A

[EXPLICACAO]
A solução mais segura é armazenar as credenciais da API no AWS Secrets Manager e recuperá-las em tempo de execução usando o SDK da AWS. Aqui está o porquê: Gerenciamento centralizado de segredos: o AWS Secrets Manager é um serviço dedicado projetado para armazenar com segurança e gerencie segredos como chaves de API, senhas e credenciais de banco de dados. Isso centraliza o gerenciamento secreto, tornando mais fácil controlar o acesso e alternar segredos. https://aws.amazon.com/secrets-manager/ Criptografia: o Secrets Manager criptografa segredos em trânsito e em repouso. Isto fornece uma forte camada de proteção contra acesso não autorizado. Controle de acesso: o Secrets Manager integra-se ao IAM, permitindo definir um controle de acesso refinado políticas que especificam quais usuários ou serviços podem acessar quais segredos. Isso restringe o acesso apenas a autorizados entidades. Auditoria: o Secrets Manager integra-se ao AWS CloudTrail, fornecendo uma trilha de auditoria de todos os acessos e eventos de modificação. Isso ajuda a rastrear e investigar quaisquer possíveis violações de segurança. Rotação: o Secrets Manager oferece suporte à rotação automática de segredos, que é uma prática de segurança crucial para minimizando o impacto de credenciais comprometidas. Recuperação sob demanda: a recuperação de segredos em tempo de execução usando o AWS SDK garante que a chave de API não seja codificado no código do aplicativo ou nos arquivos de configuração. Impacto no desempenho: a recuperação de segredos do Secrets Manager em tempo de execução tem impacto mínimo no aplicativo desempenho. O AWS SDK é otimizado para recuperação eficiente de segredos. As opções B, C e D são menos seguras: Opção B: Armazenar a chave de API em uma variável de código local e enviá-la para um repositório Git expõe o segredo para qualquer pessoa com acesso ao repositório. Este é um grave risco de segurança. Opção C: embora armazenar a chave de API em um bucket S3 com acesso restrito seja melhor que a opção B, ainda não é tão seguro quanto o Secrets Manager. O S3 foi projetado para armazenamento de objetos, não para gerenciamento de segredos. Gerenciador de segredos oferece recursos adicionais como criptografia, rotação e auditoria que são especificamente adaptados para segredos gestão. Opção D: armazenar a chave de API em uma tabela do DynamoDB com políticas baseadas em recursos também é menos seguro do que Gerenciador de segredos. Semelhante ao S3, o DynamoDB é um serviço de banco de dados, não um serviço de gerenciamento secreto, e não possui os recursos especializados do Secrets Manager. Portanto, a opção A oferece a solução mais robusta e segura para gerenciar chaves de API. Ele aproveita um serviço dedicado de gerenciamento de segredos, fornecendo criptografia, controle de acesso, auditoria e rotação capacidades. Isso minimiza o risco de credenciais comprometidas e ajuda a manter a segurança do dados e sistemas da empresa.

As informações de autenticação e URL da API deve estar disponível para todas as versões implantadas atuais e futuras do aplicativo durante o desenvolvimento, teste e ambientes de produção. [A] Atualize o aplicativo para recuperar as variáveis ​​do AWS Systems Manager Parameter Store. Use exclusivo caminhos no Parameter Store para cada variável em cada ambiente. Armazene as credenciais no AWS Secrets Manager em cada ambiente.
[B] Atualizar o aplicativo para recuperar as variáveis ​​do AWS Key Management Service (AWS KMS). Armazene o URL da API e credenciais como chaves exclusivas para cada ambiente.
[C] Atualize o aplicativo para recuperar as variáveis ​​de um arquivo criptografado que é armazenado com o aplicativo. Armazene a URL e as credenciais da API em arquivos exclusivos para cada ambiente.

Use caminhos exclusivos no Parameter Store para cada variável em cada ambiente. Loja as credenciais no AWS Secrets Manager em cada ambiente." Permite armazenar parâmetros como pares de valores-chave e é ideal para armazenar os URL da API e informações de autenticação que são comuns entre ambientes, mas podem variar um pouco (por exemplo, URLs diferentes para desenvolvimento, teste e produção). Usar caminhos exclusivos para cada ambiente garante segregação e evita conflitos. Isso se alinha com o requisito de disponibilizar essas variáveis para todas as versões em ambientes. AWS Secrets Manager: Secrets Manager foi projetado especificamente para armazenar com segurança segredos como credenciais (senhas, chaves de API, tokens, etc.). Oferece recursos como rotação automática, o que aumenta a segurança e reduz o risco de credenciais comprometidas. Armazenar credenciais separadamente de outros dados de configuração é uma melhores práticas. Menos alterações no aplicativo: esta abordagem requer a modificação do aplicativo para buscar valores do parâmetro Gerente de Loja e Segredos. Esta é uma mudança gerenciável e evita a codificação de dados confidenciais dentro do código do aplicativo ou construir artefatos. A opção D, usando a definição de tarefas do ECS, é mais entediante para manutenção em vários ambientes. Segurança: o Parameter Store oferece suporte à criptografia em repouso usando AWS KMS e ofertas do Secrets Manager rotação automática e controle de acesso mais rígido, tornando a opção A a abordagem mais segura. Escalabilidade e facilidade de manutenção: o uso do Parameter Store e do Secrets Manager é bem dimensionado com o aplicativo crescimento e simplifica o gerenciamento de configuração em vários ambientes. Alterações nas variáveis podem ser feito centralmente sem reimplantar o aplicativo (após um pequeno atraso de propagação). Vejamos por que as outras opções não são ideais: B. AWS Key Management Service (AWS KMS): embora o KMS possa criptografar dados, é principalmente um serviço de gerenciamento de chaves. serviço e menos adequado para armazenar e recuperar parâmetros de configuração ou segredos diretamente. Usando KMS diretamente envolveria uma lógica de criptografia/descriptografia mais complexa dentro do aplicativo. C. Arquivo criptografado armazenado com o aplicativo: Essa abordagem apresenta riscos de segurança significativos. Armazenando segredos em um arquivo, mesmo que criptografado, os torna mais vulneráveis a comprometimentos, especialmente se o aplicativo for comprometido. Também requer o gerenciamento de chaves de criptografia, aumentando a complexidade. D. Eles são claramente visíveis no console AWS e por meio da API e não destinado a informações confidenciais. Além disso, gerenciá-los diretamente para diversas versões e ambientes seria complicado. Esta opção também precisaria ser atualizada sempre que tivermos que alternar as credenciais, tornando-o altamente indesejável. ## Q22

[ENUNCIADO]
Um desenvolvedor está criando um aplicativo que armazenará informações pessoais de saúde (PHI). O PHI precisa ser criptografado em todos os momentos. Uma instância de banco de dados criptografada do Amazon RDS for MySQL está armazenando os dados. O desenvolvedor quer para aumentar o desempenho do aplicativo armazenando em cache os dados acessados com frequência e adicionando a capacidade de classificar ou classifique os conjuntos de dados armazenados em cache. Qual solução atenderá a esses requisitos?

[A] Crie uma instância do Amazon ElastiCache for Redis. Habilite a criptografia de dados em trânsito e em repouso. Loja dados acessados com frequência no cache.
[B] Criar uma instância do Amazon ElastiCache for Memcached. Habilite a criptografia de dados em trânsito e em repouso. Armazene dados acessados ​​com frequência no cache.
[C] Crie uma réplica de leitura do Amazon RDS para MySQL. Conecte-se à réplica de leitura usando SSL. Configurar a leitura réplica para armazenar dados acessados com frequência.
[D] Crie uma tabela Amazon DynamoDB e um cluster DynamoDB Accelerator (DAX) para a tabela. Loja dados acessados com frequência na tabela do DynamoDB.

[RESPOSTA] A

[EXPLICACAO]
A resposta correta é A. Crie uma instância do Amazon ElastiCache for Redis. Habilite a criptografia de dados em trânsito e em repouso. Armazene dados acessados ​​com frequência no cache. Aqui está uma justificativa detalhada: 1. PHI e criptografia: O aplicativo lida com PHI (informações pessoais de saúde), necessitando de end- criptografia de ponta a ponta, tanto em trânsito quanto em repouso, para cumprir regulamentações como HIPAA. Este requisito exclui imediatamente opções que não abordam explicitamente a criptografia ou dependem exclusivamente de SSL. 2. Armazenamento em cache para desempenho: o armazenamento em cache de dados acessados com frequência é uma técnica padrão para melhorar desempenho do aplicativo, reduzindo a carga no banco de dados. O ElastiCache é um gerenciamento na memória serviço de armazenamento de dados projetado especificamente para armazenamento em cache. 3. Capacidades do Redis: O ElastiCache for Redis é a melhor escolha em relação ao Memcached porque o Redis oferece estruturas de dados avançadas (como conjuntos classificados) que suportam classificação e classificação de conjuntos de dados armazenados em cache. O Memcached, por outro lado, é principalmente um armazenamento simples de valores-chave sem esses recursos. 4. Criptografia no ElastiCache for Redis: O ElastiCache for Redis oferece suporte à criptografia em repouso usando AWS Key Management Service (KMS) e criptografia em trânsito usando TLS (Transport Layer Security). Isto garante que as PHI estejam sempre protegidas. 5. ElastiCache versus réplica de leitura RDS: embora uma réplica de leitura RDS (opção C) possa descarregar o tráfego de leitura de o banco de dados primário, ainda é um banco de dados relacional. Ele não fornece acesso rápido na memória que o ElastiCache oferece. Além disso, gerenciar e dimensionar réplicas de leitura pode ser mais complexo do que usar um serviço de cache gerenciado. 6. ElastiCache versus DynamoDB com DAX: DynamoDB com DAX (opção D) é adequado para produtividade e cargas de trabalho NoSQL de baixa latência. No entanto, para simplesmente armazenar em cache os dados acessados com frequência de um banco de dados RDS existente e exigindo recursos de classificação, o Redis é um método mais apropriado e solução potencialmente rentável. O DynamoDB funciona principalmente quando o próprio banco de dados principal é DynamoDB. Em resumo, o ElastiCache for Redis com criptografia habilitada atende a todos os requisitos: armazenamento em cache para desempenho, suporte para classificação/classificação (usando conjuntos classificados do Redis) e criptografia robusta para proteger PHI. É um solução de cache dedicada que se integra perfeitamente aos serviços da AWS e é mais fácil de gerenciar do que alternativas como réplicas de leitura. Links autorizados: Amazon ElastiCache: https://aws.amazon.com/elasticache/ ElastiCache para Redis: https://aws.amazon.com/elasticache/redis/ Segurança do ElastiCache: https://docs.aws.amazon.com/AmazonElastiCache/latest/red-ug/security.html Conformidade com HIPAA: https://aws.amazon.com/compliance/hipaa/

## Q27

[ENUNCIADO]
Um desenvolvedor deseja expandir um aplicativo para execução em várias regiões da AWS. O desenvolvedor quer copiar a Amazon Imagens de máquina (AMIs) com as alterações mais recentes e crie uma nova pilha de aplicativos na região de destino. De acordo com os requisitos da empresa, todas as AMIs devem ser criptografadas em todas as regiões. No entanto, nem todos os AMIs que o os usos da empresa são criptografados. Como o desenvolvedor pode expandir o aplicativo para rodar na região de destino enquanto atende à criptografia exigência?

[A] Criar novas AMIs e especificar parâmetros de criptografia. Copie as AMIs criptografadas para a região de destino. Exclua as AMIs não criptografadas.
[B] Use o AWS Key Management Service (AWS KMS) para ativar a criptografia nas AMIs não criptografadas. Copie o AMIs criptografadas para a região de destino.
[C] Use AWS Certificate Manager (ACM) para habilitar a criptografia nas AMIs não criptografadas. Copie o criptografado AMIs para a região de destino.
[D] Copie as AMIs não criptografadas para a região de destino. Habilite a criptografia por padrão na região de destino.

[RESPOSTA] A

[EXPLICACAO]
A resposta correta é A. Eis o porquê: A opção A é a abordagem mais direta e confiável para garantir que todas as AMIs sejam criptografadas conforme necessário antes de implantar o aplicativo na nova região. Você pode criar novas AMIs a partir de AMIs não criptografadas existentes e especifique a criptografia durante o processo de criação da AMI. Isso garante que as novas AMIs sejam criptografadas de o início. A cópia dessas AMIs recém-criptografadas para a região de destino atende ao requisito de que todos As AMIs sejam criptografadas em todas as regiões. Excluir as AMIs não criptografadas é uma medida prudente para segurança e conformidade. A opção B está incorreta porque, embora você possa usar o KMS para criptografar volumes do EBS associados a instâncias do EC2, você não pode "ativar a criptografia" diretamente em uma AMI não criptografada existente usando KMS como uma única etapa. Você faria precisa criar uma nova AMI fazendo backup da AMI não criptografada e ao mesmo tempo especificando parâmetros de criptografia (semelhante à opção A). A opção C está incorreta. AWS Certificate Manager (ACM) é usado para gerenciar certificados SSL/TLS para proteger comunicações em rede. Ele não suporta criptografia AMI. Portanto, é irrelevante neste cenário. A opção D está incorreta. Embora você possa definir a criptografia por padrão em uma região, essa configuração afeta principalmente novos Volumes EBS criados nessa região. Copiar uma AMI não criptografada ainda resultará em uma AMI não criptografada no região de destino, mesmo que a criptografia por padrão esteja habilitada. Você ainda precisará criar uma nova AMI a partir do AMI não criptografada para ativar a criptografia. Portanto, criar novas AMIs com criptografia habilitada durante a criação é a abordagem correta para garantir que todos As AMIs são criptografadas e atendem aos requisitos declarados da empresa. ## Q31

[ENUNCIADO]
Um desenvolvedor tem um aplicativo que armazena dados em um bucket do Amazon S3. O aplicativo usa uma API HTTP para armazenar e recuperar objetos. Quando a operação da API PutObject adiciona objetos ao bucket S3, o desenvolvedor deve criptografar esses objetos em repouso usando criptografia no lado do servidor com chaves gerenciadas do Amazon S3 (SSE-S3). Qual solução atenderá a esse requisito?

[A] Crie uma chave do AWS Key Management Service (AWS KMS). Atribua a chave KMS ao bucket S3.
[B] Defina o cabeçalho x-amz-server-side-encryption ao invocar a operação da API PutObject.
[C] Forneça a chave de criptografia no cabeçalho HTTP de cada solicitação.
[D] Aplicar TLS para criptografar o tráfego para o bucket S3.

[RESPOSTA] B

[EXPLICACAO]
A resposta correta é B: Defina o cabeçalho x-amz-server-side-encryption ao invocar a API PutObject operação. Aqui está o porquê: O requisito é criptografar objetos em repouso no S3 usando criptografia no lado do servidor com Amazon S3 gerenciado Chaves (SSE-S3). SSE-S3 é habilitado automaticamente no nível do bucket sem a necessidade de criar nova criptografia chaves. Essa criptografia é feita pelo próprio S3 usando chaves próprias, gerenciadas pela AWS. A opção B aborda diretamente esse requisito. O cabeçalho x-amz-server-side-encryption, quando incluído no Solicitação da API PutObject, instrui S3 a criptografar o objeto usando SSE-S3. Não há gerenciamento de chaves no o lado do desenvolvedor é necessário. O S3 cuida completamente do gerenciamento de chaves, que é exatamente o que o estados de requisitos. A opção A está incorreta porque sugere o uso de chaves AWS KMS. Ao usar o AWS KMS para servidor a criptografia (SSE-KMS) é válida, não é SSE-S3, que é o requisito especificado. Também envolve mais complexidade com criação e gerenciamento de chaves. A opção C também está incorreta. Fornecer a chave de criptografia no cabeçalho HTTP implica usar Server-Side Criptografia com chaves fornecidas pelo cliente (SSE-C), onde o cliente gerencia as chaves de criptografia. Novamente, este não é SSE-S3. A opção D, aplicando TLS, criptografa os dados em trânsito, protegendo os dados à medida que eles se movem entre o aplicativo e S3. No entanto, ele não aborda a criptografia em repouso quando os dados são armazenados no bucket S3, portanto, não cumprindo o requisito declarado. Em resumo, a questão pede explicitamente o SSE-S3. Definir o cabeçalho x-amz-server-side-encryption é o maneira mais simples e direta de habilitar a criptografia SSE-S3 em objetos S3 durante a operação PutObject, com S3 cuidando automaticamente do gerenciamento de chaves. Links de referência: Criptografia do lado do servidor Amazon S3: https://docs.aws.amazon.com/AmazonS3/latest/userguide/serv-side- criptografia.html Protegendo dados usando criptografia no servidor: https://docs.aws.amazon.com/AmazonS3/latest/userguide/protecting-data-server-side-encryption.html Objeto PUT - criptografia do lado do servidor: https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html

[ENUNCIADO]
Um desenvolvedor está criando um aplicativo que inclui uma API REST do Amazon API Gateway na região us-east-2. O o desenvolvedor deseja usar o Amazon CloudFront e um nome de domínio personalizado para a API. O desenvolvedor adquiriu um Certificado SSL/TLS para o domínio de um provedor terceirizado. Como o desenvolvedor deve configurar o domínio customizado para a aplicação?

[B] Importar o certificado SSL/TLS para o CloudFront. Crie um registro DNS CNAME para o domínio personalizado.
[C] Importe o certificado SSL/TLS para o AWS Certificate Manager (ACM) na mesma região da API. Crie um Registro DNS CNAME para o domínio personalizado.
[D] Importe o certificado SSL/TLS para o AWS Certificate Manager (ACM) na região us-east-1. Crie um DNS Registro CNAME para o domínio personalizado.

[RESPOSTA] D

[EXPLICACAO]
A resposta correta é D. Eis o porquê: Ao usar um domínio personalizado com CloudFront e API Gateway, o certificado SSL/TLS deve residir na AWS Certificate Manager (ACM) na região us-east-1 (Norte da Virgínia), independentemente de onde o API Gateway ou A distribuição do CloudFront está localizada. Este é um requisito específico do CloudFront para certificados SSL personalizados. O CloudFront é um serviço global, e os certificados ACM usados com domínios personalizados do CloudFront devem estar nos EUA Região Leste (Norte da Virgínia), porque é onde a infraestrutura do CloudFront que lida com SSL/TLS terminação para domínios personalizados está localizada. Isso direciona o tráfego do seu domínio personalizado para a distribuição do CloudFront, que então o encaminha para o API Gateway subjacente. A opção A está incorreta porque coloca o certificado na região us-east-2, o que é incorreto para o CloudFront. Ele também usa um registro DNS A, enquanto um CNAME é necessário. A opção B está incorreta porque você não importa certificados diretamente para o CloudFront. Os certificados são gerenciados dentro da ACM. A opção C está incorreta porque o certificado está armazenado em us-east-2, que não é compatível com CloudFront. Em resumo, para que um domínio personalizado e um certificado SSL/TLS funcionem com o CloudFront, você deve: 1. Importar o certificado na ACM na região us-east-1. 2. Crie um registro CNAME em suas configurações de DNS que aponte seu domínio personalizado ao nome de domínio da sua distribuição do CloudFront. Referências: Documentação da AWS - Usando nomes de domínio alternativos (CNAMEs): https://docs.aws.amazon.com/cloudfront/latest/developerguide/using-alternate-domain-names.html Documentação da AWS – Regiões onde você pode solicitar ou importar certificados ACM: https://docs.aws.amazon.com/acm/latest/userguide/acm-regions.html

## Q37

[ENUNCIADO]
Uma empresa possui um bucket do Amazon S3 que contém dados confidenciais. Os dados devem ser criptografados em trânsito e em descanse. A empresa criptografa os dados no bucket S3 usando uma chave AWS Key Management Service (AWS KMS). Um desenvolvedor precisa conceder a várias outras contas da AWS permissão para usar a operação GetObject do S3 para recuperar os dados do bucket S3. Como o desenvolvedor pode garantir que todas as solicitações para recuperar os dados forneçam criptografia em trânsito?

[A] Definir uma política baseada em recursos no bucket S3 para negar acesso quando uma solicitação atender à condição “aws:SecureTransport”: “falso”.
[B] Definir uma política baseada em recursos no bucket S3 para permitir o acesso quando uma solicitação atender à condição “aws:SecureTransport”: “falso”.
[C] Definir uma política baseada em funções nas funções de outras contas para negar acesso quando uma solicitação atender à condição de “aws:SecureTransport”: “falso”.
[D] Definir uma política baseada em recursos na chave KMS para negar acesso quando uma solicitação atender à condição de “aws:SecureTransport”: “falso”.

[RESPOSTA] A

[EXPLICACAO]
A resposta correta é A. Eis o porquê: O requisito é impor criptografia em trânsito para todas as solicitações GetObject para um bucket S3 contendo dados sensíveis. Criptografia em trânsito significa que os dados são criptografados enquanto são transferidos entre o cliente e o balde S3. HTTPS garante essa criptografia usando TLS/SSL. A opção A está correta porque aproveita uma política de bucket S3 (uma política baseada em recursos) para negar acesso quando um a solicitação não usa transporte seguro (HTTPS). A condição “aws:SecureTransport”: “false” especificamente verifica se a solicitação não está usando HTTPS. Ao negar o acesso nesta condição, a política força efectivamente todas as solicitações bem-sucedidas para usar HTTPS, cumprindo assim o requisito de criptografia em trânsito. A opção B está incorreta porque permitir acesso quando “aws:SecureTransport”: “false” permitiria acesso não criptografado tráfego, contradizendo diretamente a exigência. A opção C está incorreta porque as políticas baseadas em funções são anexadas às funções do IAM assumidas pelo solicitante contas, não diretamente para o recurso de bucket S3. Embora você possa, teoricamente, gerenciá-lo por meio de funções, é mais complexo e menos direto do que usar uma política baseada em recursos no próprio bucket S3. Além disso, este exigiria coordenação e modificação em todas as contas que necessitam de acesso, tornando-a menos sustentável. A opção D está incorreta porque a política de chave KMS controla principalmente quem pode usar a chave KMS para criptografia e descriptografia, não se a transferência de dados de e para o S3 usa criptografia em trânsito (HTTPS). Enquanto o dados são criptografados em repouso usando KMS, esta é uma preocupação separada da criptografia em trânsito imposta por HTTPS. A política de chave KMS não estaria diretamente envolvida na aplicação de HTTPS para solicitações GetObject. Em resumo, as políticas de bucket do S3 oferecem uma maneira simples e gerenciada centralmente de impor a criptografia em trânsito usando a condição aws:SecureTransport. Ao negar solicitações não-HTTPS, você efetivamente obriga o uso de HTTPS para acessar o conteúdo do bucket S3. ## Q38

[ENUNCIADO]
Um aplicativo hospedado em uma instância do Amazon EC2 precisa de acesso aos arquivos armazenados em um Amazon S3 balde. O aplicativo lista os objetos armazenados no bucket S3 e exibe uma tabela ao usuário. Durante teste, um desenvolvedor descobre que o aplicativo não mostra nenhum objeto na lista. Qual é a maneira MAIS segura de resolver esse problema?

[A] Atualizar o perfil da instância do IAM anexado à instância do EC2 para incluir a permissão S3:* para o S3 balde.
[B] Atualizar o perfil da instância IAM anexado à instância EC2 para incluir a permissão S3:ListBucket para o balde S3.

[RESPOSTA] B

[EXPLICACAO]
A resposta correta é B: atualize o perfil da instância do IAM anexado à instância do EC2 para incluir o Permissão S3:ListBucket para o bucket S3. Aqui está uma justificativa detalhada: O problema principal é que a instância EC2, que hospeda o aplicativo, não tem a permissão necessária para listar o conteúdo do balde S3. Como o aplicativo em execução na instância EC2 precisa interagir com o S3, o mais O método seguro e apropriado é conceder permissões à instância do EC2 por meio de uma função IAM. Isso evita incorporar credenciais diretamente no aplicativo ou conceder permissões desnecessárias a indivíduos desenvolvedores. A opção B aborda isso precisamente adicionando a permissão S3:ListBucket ao perfil da instância do IAM associado à instância EC2. Esta permissão permite que a instância do EC2 liste os objetos dentro do intervalo S3 especificado. A opção A, conceder S3:* (todas as permissões S3), viola o princípio do menor privilégio. É melhor conceder apenas as permissões específicas necessárias. A opção C, atualizar as permissões de usuário do desenvolvedor, está incorreta. Portanto, conceder à instância EC2 a permissão menos privilegiada necessária (S3:ListBucket) por meio de um IAM a função anexada à instância é a solução mais segura e eficiente. ## Q77

[ENUNCIADO]
Um aplicativo em desenvolvimento é necessário para armazenar centenas de arquivos de vídeo. Os dados devem ser criptografados dentro o aplicativo antes do armazenamento, com uma chave exclusiva para cada arquivo de vídeo. Como o desenvolvedor deve codificar o aplicativo?

[A] Use a API KMS Encrypt para criptografar os dados. Armazene a chave de dados e os dados criptografados.
[B] Use uma biblioteca de criptografia para gerar uma chave de criptografia para o aplicativo. Use a chave de criptografia para criptografar os dados. Armazene os dados criptografados.

[EXPLICACAO]

Isto elimina diretamente as opções de criptografia do lado do servidor. KMS para gerenciamento de chaves: o AWS KMS foi projetado para gerenciamento seguro de chaves. Em vez de criar e gerenciando chaves manualmente (Opção B), o KMS oferece um serviço seguro e gerenciado para criar, armazenar e controlar o chaves de criptografia usadas para criptografar seus dados. API GenerateDataKey: A API GenerateDataKey aborda especificamente o cenário em que você precisa de um único chave para criptografar um grande número de objetos de dados. Ele gera uma chave de dados (usada para criptografar o arquivo de vídeo) e o criptografa usando uma chave KMS que você controla. Criptografia de envelope: esta abordagem utiliza criptografia de envelope, uma prática de segurança padrão. Você usa um dado chave gerada e criptografada pelo KMS para realmente criptografar os dados. A chave de dados criptografada é então armazenada junto com os dados criptografados. Você teria para lidar com a geração, armazenamento, rotação e controle de acesso de chaves, que o KMS cuida para você. D (criptografia do lado do servidor S3): a criptografia do lado do servidor ocorre depois que os dados chegam ao S3. O requisito é criptografar antes do armazenamento no aplicativo. Em resumo, o uso do GenerateDataKey permite transferir o gerenciamento de chaves para o AWS KMS, fornecendo uma experiência mais solução segura e escalável, ao mesmo tempo que atende aos requisitos de chaves exclusivas para cada arquivo de vídeo e cliente- criptografia lateral.
